# Three Business Model Architectures — Cycle 1 Draft

All three are Level C (hypothesis). Each is evaluated against the AMOR 2020 evidence base,
not invented from scratch.

## Architecture A — Managed Maintenance Transformation
**What it is:** A large industrial services provider runs the customer's maintenance
function under a staged commercial model (open book → fixed price), explicitly modeled on
what AMOR 2020 actually proposed and evidenced — contractor integration, org
right-sizing, HOTT improvement — but delivered by an existing large provider's balance
sheet and multi-site capability instead of a single-site MBO spinout.
**Revenue logic:** Management fee + fixed-scope fee, with transformation project fees during
ramp-up. No performance fee, no gainshare.
**Strength:** Fully evidenced by AMOR 2020 — pools 1, 2, and 3a (`05_VALUE_POOLS/`) are
provider-controlled and cleanly attributable. Lowest execution risk of the three.
**Weakness:** This is essentially AMOR 2020 with a bigger balance sheet behind it. It does
not test the core AMOR 2030 thesis (performance-based value) at all — it's the "Labour
Provider → Integrated Maintenance Partner" rungs only. Margin profile is a managed-services
margin, not a performance-partner margin.

## Architecture B — Asset Performance Partnership
**What it is:** Adds a performance layer on top of Architecture A: a Base Fee plus a
Performance Fee tied to a small number of payment-eligible KPIs, restricted to the pools
proven provider-controlled in Cycle 1 (contractor management, own-org efficiency, workflow
scheduling — pool 3a). Lifecycle/reliability (pool 4) and work-permit delay (pool 3b) stay
as context/management KPIs only, not payment KPIs, until a Performance Attribution Matrix
and joint SLA exist (Gate 2).
**Revenue logic:** Base Fee (fixed, covers baseline delivery) + Performance Fee (capped,
tied only to attribution-clean KPIs) + optional Digital/Transformation project revenue.
**Strength:** Directly tests the core thesis, but only on the value pools where attribution
is actually defensible today — disciplined, not aspirational.
**Weakness:** The two largest "potential" pools in AMOR 2020 (lifecycle/reliability at
€5-15m/yr, and the permit-delay half of HOTT) are deliberately excluded from payment
mechanisms in this architecture, which caps how big the performance-fee story can be told
in year 1-2. That's a feature (credibility) framed as a bug (smaller headline number) —
worth flagging explicitly to Petri and the CFO audience rather than hiding it.

## Architecture C — Outcome-Based Asset Performance Platform
**What it is:** The full protocol vision — Base Fee + Performance Fee + Gainshare + capped
Painshare, spanning all five value pools including lifecycle/reliability and full HOTT,
governed by a Joint Asset Performance Board and Value Validation Board, with a genuine
multi-site Standard Core / Configurable Module architecture from day one.
**Revenue logic:** Full Phase 0-4 staged model per protocol Section 9.
**Strength:** This is the actual destination of the working thesis and the ladder in
`STRATEGIC_THESIS.md` — Reliability Partner through Outcome-Based Strategic Partner.
**Weakness — material:** Nothing in the evidence base supports this today. AMOR 2020 never
attempted attribution, gainshare, or painshare on anything. Attempting Architecture C as a
day-1 commercial model repeats the exact credibility failure identified in
`05_VALUE_POOLS/value_pool_tree.md` (unreconciled "potential" vs. committed numbers) at
higher stakes, because real gainshare payments (not just marketing claims) would be on the
line. Architecture C is the right long-term shape but is not fundable as a Phase 1 pitch on
today's evidence.
