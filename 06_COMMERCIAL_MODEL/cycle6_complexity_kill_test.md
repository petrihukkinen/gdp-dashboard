## Task 3 — Attacking Event 1 and Event 3

### Event 1 attack
Real, previously unaddressed gaps found: (a) **baseline-inflation gaming** — nothing
currently requires external market-rate verification of the frozen pre-transition baseline,
leaving room for a collusive inflated starting point; (b) **job-complexity catalog
maintenance is a real, ongoing cost**, not a one-time setup, since job types evolve; (c)
**labour substitution** — a "rate improvement" achieved by substituting lower-skilled labour
on the same job code is not genuine productivity value, and nothing currently distinguishes
this from real efficiency gains; (d) **no re-baselining trigger exists for customer-driven
procurement policy changes** (e.g. a new mandated supplier framework), which could
artificially move the baseline. None of these are fatal — all are fixable via contract
mechanism refinements (external rate-card cross-check, catalog governance, a rework/quality
cross-check analogous to Event 9's, a procurement-change re-baseline clause). **Verdict:
Event 1 survives as CORE, with four required contract-mechanism fixes logged, not yet
built.** Its structural strength versus Event 3 — it prices an *actual measured invoice
delta* against a frozen baseline, not a counterfactual — remains decisive.

### Event 3 attack
More serious. Confirmed: low frequency (3-4/yr, likely declining over time as reliability
improves — a self-limiting revenue mechanism, which is a sign of the underlying model
working, not a flaw, but does cap its long-run commercial density further); the
counterfactual problem is structural and doesn't fully resolve with more rigor; the 180-day
settlement delay is real; the Causal Connection Map is a genuinely large, unsized fixed cost;
secondary-failure netting adds real complexity and payment-timing uncertainty on top of an
already-complex primary claim; the ≥3-prior-failures qualifying threshold is exposed to CMMS
classification manipulation (tied to the Event 8 data-quality gate); and the core
psychological objection — paying for an absence — has no purely methodological fix.

**Verdict: Event 3 as originally designed (per-event case-by-case dollar-value gainshare)
does not survive. It is killed, not preserved to protect prior cycles' work.**

**Restructured successor — Annual Reliability Event Reward:** instead of proving and
adjudicating an individual euro value for every qualifying avoided failure, the contract
pre-agrees a **fixed reward per qualifying reliability event** (illustrative: €150,000 per
qualifying bad-actor resolution — a number to be negotiated, not invented as fact here). The
Value Validation Board's job becomes counting how many qualifying events occurred in a year
— still using the existing qualification criteria unchanged (≥3 prior failures, joint RCA,
documented intervention, envelope compliance, Causal Connection Map) — rather than proving
each event's specific dollar magnitude. This is a **subtraction**, not a new mechanism: it
removes the per-event financial-proof burden and converts quarterly case-by-case
adjudication into a single annual settlement, while keeping every qualification safeguard
built in Cycles 2-5 intact. Net effect: same rigor on *whether* an event qualifies, radically
less effort on *how much* it's worth.

## Task 4 — Reclassifying Event 4

Compared: (A) event-level painshare claims as currently designed, (B) a pure contractual
downside/liability adjustment mechanism, (C) a risk-corridor trigger with only material
cases individually adjudicated.

**Recommendation: (C), reframed via (B)'s language.** The full decision tree (unchanged,
Step 3.6 included) stays exactly as designed — this is Operating Control / Contract
Mechanism infrastructure, invoked only when needed. What changes is how Event 4 is presented
and governed commercially: it should **not** be marketed or administered as a routine
"payment event" alongside Event 1 — that framing implies a regular claims cadence Event 4
should never actually have in a well-run contract. It is a **downside corridor** that
activates rarely, by design, and calling it anything else creates a false expectation of
bureaucratic regularity. This is a relabeling with real commercial-narrative consequences,
not a substantive redesign — the caps, decision tree, and clawback are untouched.

## Task 5 — Event 9 Modularity Test

Compared four options; **recommendation: bundle Event 5 (TA scope reduction) and Event 9
(TA Execution Efficiency) into a single, optional Turnaround Value Module**, activated only
for contracts where (a) the provider holds genuine TA execution responsibility and (b) TAs
are frequent/large enough to justify the fixed cost of maintaining Event 9's independence
relationship and Event 5's condition-(c) governance. **Default state for both events in the
core commercial model: reporting only.** This directly matches Model C's "activated only for
agreed value pools" design already established in Cycle 5, and avoids forcing TA complexity
onto customers who don't need it.

## Task 7 — 15-Minute CFO Test

**Minimum CFO-level commercial explanation (≈180 words):**

> "AMOR pays the way a Full Service maintenance contract already does — a base fee for
> delivery. On top of that, three things happen. First, when we get you a better deal from
> contractors than you paid before, we split that saving with you — you keep the majority,
> paid monthly, based on your own invoices. Second, once a year, we review any repeat
> equipment failures we've genuinely fixed for good, using your own data and a joint
> sign-off process, and if it's proven, you pay a pre-agreed reward per fix. Third, if we
> cause you a major production loss through our own maintenance failure — not your
> operating decisions, not equipment we don't manage — we pay you back, capped so it's real
> but bounded, never open-ended. If turnarounds are a big part of your operation, we can add
> a fourth, optional piece just for that. Everything is reviewed by a joint board — you and
> us, equally represented — so neither side can declare itself the winner."

This does not require MII/RRE formulas, the full Event 4 decision tree, complete VVB
procedures, intervention-netting methodology, or six separate event definitions.
**Does the commercial story require technical appendix detail to be credible? No — it stands
on ordinary B2B trust that "a joint process exists," the same way any SLA-based contract
does.** Verdict: **PASS.**

**Four-bucket separation:**
1. **Commercial Story:** the paragraph above.
2. **Contract Mechanism:** Event 1's rate methodology and catalog; Event 3-simplified's
   qualification criteria and pre-agreed reward figure; Event 4's materiality gate, caps,
   collar, clawback; Turnaround Module activation terms.
3. **Operating Control:** MII/RRE monitoring, the full Event 4 decision tree, intervention
   netting mechanics, the Causal Connection Map, Event 9 independence criteria, VVB
   cadence/quorum/escalation detail.
4. **Technical Appendix:** formulas, evidence-tier hierarchies, decision-tree step logic,
   ordinal scoring methodology — reference material for disputes, audits, and legal review.

## Task 8 — Bureaucracy Break-Even Test

Illustrative fully-loaded cost per claim (blended rate ~€150/hr, illustrative): Event
1-type ~€450/claim; Event 3-simplified's annual review ~€2,000-3,000 total (one settlement
covering all qualifying events that year, not per-event); Event 4 ~€9,000/claim when it
fires; Turnaround Module claims ~€12,000/claim (rare).

| Annual claim volume | Assessment |
|---|---|
| 5 | Trivial — no dedicated administrative capacity needed |
| 10 | Trivial |
| 25 | Manageable in aggregate cost, but if a meaningful share are high-effort (Event 4/module) types, starts to require dedicated part-time claims capacity on both sides |
| 50 | **Likely break point** — not primarily a cost problem (still a small fraction of contract value) but a **VVB attention-bandwidth problem**: a board built for monthly/quarterly cadence cannot batch-process high-effort claims at this velocity |
| 100 | Almost certainly unsustainable under the current VVB design (parity voting, quorum, evidence-completeness declarations); a volume this high is itself a signal something upstream is wrong (over-pursuit of low-value claims, Gate A/C failures not being enforced) |

**Bureaucracy break point: ~25-40 claims/year, driven by claim-type mix and VVB bandwidth,
not aggregate cost.** Architecture Z's baseline (~13-15/yr) sits at roughly 40-60% of this
conservative estimate — real headroom, achieved by construction (fewer, better-chosen
events), not by adding a new governance tier, consistent with "prefer fewer claims."

## Task 9 — Commercial Red Team on the Reduced Architecture (Z)

1. **"This is just a complicated bonus scheme."** Partially true at the mechanics level —
   what's different is the joint-governance rigor underneath, but if the CFO pitch doesn't
   actively make that case, the objection lands. **Real, only partially answerable risk.**
2. **Customer refuses to fund avoided-failure value**, even in simplified form. Real risk
   specific to Y/Z. **Fallback: Architecture X**, which avoids this exposure entirely — worth
   stating explicitly as a negotiating fallback, not a defeat.
3. **Provider cannot forecast variable revenue.** True and structurally unavoidable in any
   variable-comp model; mitigated, not eliminated, by fewer, simpler events.
4. **Finance cannot budget annual payments.** Mitigated by Event 3-simplified's predictable
   annual timing and Event 1's small monthly increments — genuinely better than the original
   architecture's less predictable cadence.
5. **Only 1-2 qualifying Event 3-simplified events occur in a year.** Expected in a mature,
   well-run contract (fewer bad actors is a good outcome) — an expectation-setting issue at
   sale, not an architectural flaw.
6. **180-day netting delays most upside.** Substantially mitigated for Event 3-simplified by
   its own annual cadence (the observation window mostly elapses within the same cycle for
   early-year interventions); late-year interventions still spill into the next settlement —
   a smaller residual issue than in the original design.
7. **Event 1 becomes a permanent audit exercise.** True — "lowest burden of the six" is
   relative, not zero; ongoing catalog maintenance and baseline-integrity monitoring (Task 3)
   are real, indefinite costs, not one-time setup.
8. **Event 4 creates adversarial behaviour.** Reclassification helps the sales conversation
   and reduces perceived routine bureaucracy but does **not** remove the adversarial dynamic
   on the (hopefully rare) occasions it actually fires — disclosed, not solved.
9. **Turnaround module activated only on easy turnarounds.** Real, specific gaming risk in
   Z's optional-module design — cherry-picking favorable TAs for gainshare exposure while
   declining the module for risky ones. **Requires a minimum-term commitment rule (module
   election applies to all subsequent TAs for a minimum period, not selectable TA-by-TA) —
   flagged as a required Cycle 7 fix, not resolved here.**
10. **Sales team cannot explain the model consistently.** Training/enablement risk, sharply
    reduced by the ~180-word pitch versus the original six-event technical framework — itself
    the strongest practical argument for why this subtraction exercise mattered.

**None of the 10 attacks are fatal to Architecture Z. Three (bonus-scheme perception,
reliability-value refusal, TA-module cherry-picking) are real and unresolved.**
